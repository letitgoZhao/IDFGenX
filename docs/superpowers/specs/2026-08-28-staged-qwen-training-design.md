# IDFGenX 分阶段 Qwen 训练设计

> 日期：2026-08-28
> 任务：IDFGX-X-006
> 状态：待书面审核

## 1. 背景与问题

现有训练方案已经区分 1.7B Smoke、4B 主模型和可选 8B，但把 RTX 4090
视为主要开发硬件，并把 Qwen3-4B 固定为生产与论文主模型。项目实际可持续
使用的本地设备为 Y7000P、RTX 4060 Laptop GPU 8GB。训练代码、数据读取、
loss mask、checkpoint、评估和端到端 Compiler 链路若只能在云端调试，会显著
增加反馈时间和资源成本。

Qwen3 官方稠密模型没有名为“1B”的标准档位。本设计将用户提出的“1B”
明确映射为官方 `Qwen/Qwen3-1.7B`，并以 `Qwen/Qwen3-0.6B`、
`Qwen/Qwen3-1.7B`、`Qwen/Qwen3-8B` 形成三级主线。

## 2. 目标与边界

目标是让本地设备承担高频、低成本、可复现的训练验证，让云端资源只承担
已通过本地门禁的规模化实验和最终模型训练。

本设计不改变以下边界：

- 生产路线仍为 `Prompt → ScenarioSpecDraft → Resolver → Compiler → IDF`；
- Direct-All 和 Direct-Fragment 仍是隔离的论文基线；
- 训练只读取冻结 release，测试集不参与调参；
- 默认继续使用 BF16 标准 LoRA，不采用 4-bit/8-bit 量化训练；
- 几何、对象引用和 EnergyPlus 修补仍由确定性代码负责。

本任务只更新架构与实施文档，不下载模型、不安装训练依赖、不运行训练，
也不生成 Adapter、模型权重或数据产物。

## 3. 备选方案

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 保持 1.7B→4B，8B 可选 | 改动最少，延续原计划 | 本地 8GB 调试门不完整，4B 仍依赖更大显存 | 不选 |
| 0.6B→1.7B→8B+ 分阶段 | 本地反馈快，云端成本集中，最终容量更高 | 需要明确小模型与大模型结果不可直接等同 | 选择 |
| 只用 0.6B 本地、直接 8B 云端 | 流程最短 | 缺少较可信的本地效果候选，云端调参风险较高 | 不选 |

Qwen3-4B 不再是必经生产门，但保留为可选中间对照或云端资源受限时的回退，
避免为了维持旧计划额外消耗一次完整训练周期。

## 4. 分阶段模型与职责

| 阶段 | 基础模型 | 主要硬件 | 职责 | 不用于 |
| --- | --- | --- | --- | --- |
| L0 本地 Smoke | Qwen3-0.6B | RTX 4060 8GB | 验证 loader、tokenizer、loss mask、反向传播、checkpoint、小评估和端到端调用 | 生产结论、论文主成绩 |
| L1 本地候选 | Qwen3-1.7B | RTX 4060 8GB | 迭代数据配比、Prompt、LoRA 模块、rank/学习率候选和错误分析 | 替代 8B 正式评估 |
| C1 云端 Pilot | Qwen3-8B | 云端大显存 GPU | 在 10K Pilot 上重新确认超参、Spec 路线和 Direct 基线 | 未过本地门时盲目长训 |
| C2 云端 Scale | Qwen3-8B | 云端训练资源 | 50K 正式训练、消融和最终 Adapter 候选 | 用训练集替代固定测试 |
| C3 可选上界 | Qwen3-14B 及以上 | 经预算批准的云端资源 | 仅在 8B 仍显示容量瓶颈且收益覆盖成本时验证上界 | 默认项目完成条件 |

各阶段必须固定精确基础模型 revision、tokenizer revision、数据版本、代码提交、
训练配置、随机种子、硬件环境、峰值显存、吞吐和评估结果。

## 5. 本地 RTX 4060 8GB 资源策略

RTX 4060 8GB 是受支持的本地训练验证目标，不是未经验证的性能承诺。0.6B
必须首先完成 BF16 标准 LoRA smoke；1.7B 只有在实际峰值显存验证通过后，
才进入本地候选训练。

本地默认使用 micro-batch 1、梯度累积和 gradient checkpointing。发生 OOM 时，
依次检查训练实现、缩小 micro-batch、调整 checkpointing 和限制本地 smoke
样本的目标长度分布；不得静默截断样本，也不得为了宣称可运行而默认改用
4-bit/8-bit 量化。无法在 8GB 内满足门禁时，1.7B 迁移到云端，0.6B 继续承担
本地回归门。

## 6. 晋级门与数据流

```text
冻结 M1 release
    ↓
0.6B / 1K Smoke：训练链路与端到端门
    ↓
1.7B / 本地候选：效果、错误和超参方向
    ↓
8B / 10K Pilot：重新验证超参与路线
    ↓
8B / 50K Scale：正式训练、消融与发布候选
    ↓
可选 100K 数据或 14B+：仅由边际收益触发
```

L0 至少通过：无静默截断、loss mask 正确、checkpoint 可恢复、Adapter 可加载、
严格 JSON 和小规模端到端 Compiler 指标可产出。L1 必须相对未微调基线呈现
稳定改进，并完成主要失败分类。进入 C1 时重新验证学习率、LoRA rank、目标
模块、序列预算和 batch；小模型最优超参不能直接视为 8B 最优超参。

C1 决定是否进入 50K、Direct 基线是否需要随主方法扩到 50K，以及 4B 是否
有必要作为成本对照；Direct-All/Direct-Fragment 的同基座 Pilot 公平比较仍是
论文必需项。C2 达到冻结测试集门槛后才发布生产候选。100K 数据或 14B+
模型均不是默认完成条件，必须有 8B 的误差、容量或边际收益证据。

## 7. 评估与论文公平性

本地 0.6B/1.7B 结果用于工程验证、早期消融和失败诊断，必须标注为开发结果。
论文主方法 E2 与 Direct 基线 E3/E4 应使用同一 Qwen3-8B revision、相同 split、
匹配的训练 token/算力预算和统一 EnergyPlus 门禁。若云端预算不足以完成全部
8B Direct 基线，应在实验协议冻结前缩小共同样本规模，不能混用 1.7B Direct
结果与 8B Spec 结果宣称公平胜负。

模型规模本身作为独立消融：0.6B、1.7B、可选 4B、8B。最终 test 只在路线、
checkpoint 选择和重试策略冻结后运行；本地反复查看的诊断集合不得充当最终
test。

## 8. 部署出口

开发环境保留 Transformers backend，可加载 0.6B/1.7B Adapter 完成本地演示、
API contract 和端到端回归。正式服务默认部署通过 C2 门禁的 8B Spec Adapter，
基础模型与 Adapter revision 由 Model Manifest 固定。

如果最终 1.7B 已满足产品门槛，它可以作为低资源部署档，但不能自动替代论文
主模型；如果 8B 无法相对 1.7B 提供足够收益，则允许基于统一指标选择 1.7B
作为生产模型，并在 ADR/评估报告中记录成本—效果依据。14B+ 只作为可选上界，
不成为服务上线的强制依赖。

## 10. 验证与完成标准

文档更新后必须满足：

1. 不再存在“Qwen3-4B 是固定生产主线”或“只有 4090 才能开发”的有效表述；
2. 0.6B、1.7B、8B+ 的职责、数据规模、硬件和门禁没有冲突；
3. 所有训练仍要求冻结 release、无静默截断和完整 manifest；
4. 正式 Spec/Direct 比较使用同一 8B revision，或在预注册协议中统一降档；
5. 8GB 可行性用实际显存 smoke 验证，不把理论估算写成完成证据；
6. 4B 保留为可选对照/回退，不再阻塞项目主线；
7. 100K 数据与 14B+ 模型均由边际收益触发，不成为默认完成条件；
8. 不提交模型权重、数据集、训练产物、密钥或 `.env`。
